# 좌석·재접속·리바이 실사용 테스트 체크리스트 (FT-TEST-012)

작성: 2026-11-25 KST · Claude Code · 대상 브랜치 `feature/seat-management`. 정책·설계는 [좌석 관리](seat-management.md), 배포·백업·롤백 절차는 같은 문서 12절.

대상: `feature/seat-management`를 테스트 Railway + Cloudflare Preview 별칭에 배포한 뒤(별도 승인) 실제 기기로 진행한다. 운영 서버·운영 Supabase는 쓰지 않는다. 결과는 항목별 통과/실패와 시각(KST)·기기·방 코드를 [체크리스트](DEVELOPMENT_CHECKLIST.md) `FT-TEST-012` 검증 결과에 남긴다. 칩 값은 각 단계 전후로 화면의 숫자를 적어 둔다.

## 공통 준비

- [ ] 기기·브라우저 목록 기록(예: iPhone Safari, Android Chrome, PC Chrome). 6인 테스트는 실제 사람 6명 또는 기기 6대(같은 PC의 서로 다른 브라우저 프로필 가능, 단 계정은 모두 달라야 함)
- [ ] 모두 Preview 주소로 접속, 익명 로그인·닉네임 설정 완료. 설치형 네이티브 앱은 사용하지 않는다(구버전 앱은 새 서버에서 착석 불가)
- [ ] 방장이 방 생성 → 방 설정 5단계(시작 칩·SB·BB·제한 시간·리바이 1회 최대) 값 기록
- [ ] 테스트 중 테스트 Railway 로그 화면을 함께 열어 두고 시각을 맞춘다. 좌석 진단 로그(`SEAT_EVENT_LOG`, 기본 켜짐)로 아래 이벤트를 확인한다([좌석 관리](seat-management.md) 12.1절)
  - `seat_hold`(started·reclaimed·expired), `seat_released`(voluntary·expired), `auto_action`(check·fold, `offlineMs`), `membership_takeover`, `rebuy`(requested·approved·rejected·cancelled·host_granted·applied·dropped_limit·duplicate_ignored), `chip_audit`(핸드마다 `ok:true`, 실패 시 `level:error`·`kind:excess|missing`)
  - 계정은 `accountRef`, 방은 `roomRef`(해시)로만 나온다. 테스트 기록에는 방 코드 대신 `roomRef`를 함께 적어 두면 로그와 맞출 수 있다

## A. 2인 (방장 A, 손님 B)

1. [ ] A 입장 직후 미착석, 6개 좌석 표시 → A가 좌석 선택 시 즉시 착석
2. [ ] B 초대 링크 입장 → 좌석 선택 시 "승인 대기" → A 화면에 요청자·좌석·보유 칩 → 거절 → B 화면 거절 안내 → 재요청 → 승인
3. [ ] "홀덤 시작" → 핸드 진행(체크·콜·레이즈·폴드) → 칩 합계 = 시작 칩×2 유지
4. [ ] **2초 유예(재접속)**: B 차례에 B가 새로고침 → 2초 안에 복귀하면 B 차례·카드·칩 그대로, 자동 행동 없음
5. [ ] **2초 유예(자동 처리)**: B 차례에 B가 탭/앱을 완전히 닫음 → 약 2초 후 체크 가능하면 체크, 아니면 폴드. A 화면에서 B "연결 끊김 · 자리 보존 중"
6. [ ] B가 1분 안에 같은 기기로 복귀 → 같은 좌석·칩, 승인 없이 이어서 플레이(이미 실행된 자동 행동은 그대로)
7. [ ] B가 **다른 기기**에서 같은 계정으로 로그인해 복귀 → 같은 좌석·칩 복구, 처음 기기에는 "다른 기기에서 로그인" 안내
8. [ ] **3분 보존**: B가 끊긴 채 3분 이상 대기(핸드 진행 중이었다면 그 핸드가 끝날 때까지 좌석 유지) → 좌석 해제, B는 관전자 → B 복귀 시 보유 칩 유지, 재착석에 방장 승인 필요
9. [ ] B "자리에서 일어나기"(핸드 중) → "이번 판이 끝나면…" 안내 → 핸드 종료 후 관전자, 칩 유지 → 재착석 요청 → 승인 → 다음 판부터 카드
10. [ ] **리바이**: B "칩 추가 요청" → 입력창·예상 칩 표시 → A 화면 요청자·보유·요청·승인 후 예상 칩 → 승인 → 핸드 중이면 "이번 판 끝나면 반영", 끝난 뒤 칩 증가
11. [ ] 리바이 거절 → 칩 불변, 거절 안내
12. [ ] 리바이 한도: 기본값(시작 칩과 같음)보다 큰 수 입력 시 요청 불가 안내 → A가 방 설정에서 한도 변경(대기실) → 칩 초기화 없이 한도만 바뀌는지
13. [ ] 방장 A "칩 추가" → 승인 없이 즉시(핸드 중이면 판 종료 후) 증가, B 화면에 A의 요청이 보이지 않음
14. [ ] 끝: 두 사람 칩 합 = 시작 칩×2 + 승인된 리바이 합(방장 포함). 서버 로그 `chip_audit`이 모두 `ok:true`, `level:error` 0

## B. 4인 (A 방장, B·C·D)

1. [ ] 네 명 착석(좌석 번호를 일부러 띄워서: 1·2·4·6) → 딜러·SB·BB 순서가 좌석 순(시계 방향)인지 2~3핸드 확인
2. [ ] 핸드 중 D가 방에 새로 들어와 착석 요청 → 승인돼도 현재 핸드 미참여 → 다음 판부터 카드(빈 좌석을 건너뛰는 딜러 순환도 확인)
3. [ ] 같은 핸드 안에서 동시에: C 일어서기 예약, B 리바이 승인(B 핸드 참여 중), D 연결 끊김 → 핸드 종료 시 C 관전자, B 칩 = 결과 + 리바이, D 좌석 보존·다음 판 미참여
4. [ ] 올인·사이드팟 1회 이상(리바이로 스택을 다르게 만든 뒤) → 팟 분배가 화면·결과 기록과 일치, 끊긴 플레이어가 끼어 있어도 정산 정상
5. [ ] 2명이 거의 동시에 같은 빈 좌석 요청 → 하나만 대기, 다른 하나는 거부 안내
6. [ ] 방장 A가 새로고침·다른 기기 복귀 → 방장 권한·승인 목록 유지
7. [ ] 끝: 네 명 칩 합 = 시작 칩×4 + 승인 리바이 합. 결과 기록(오늘의 기록·핸드 리뷰) 이상 없음, `chip_audit` 전부 `ok:true`

## C. 6인 (최대 인원)

1. [ ] 6명 전원 착석, 7번째 입장 시도 → "방이 가득 찼어요"
2. [ ] 6인 핸드 3판 이상: 차례 이동, 타이머, 카드 공개·효과음 지연 체감 기록(느림이 있으면 시각 기록)
3. [ ] 2명 동시 연결 끊김(서로 다른 차례) → 각자 2초 후 자동 처리, 판 정체 없음
4. [ ] 1명 일어서기 → 5인으로 다음 판, 빈 좌석에 다른 사람 착석 요청·승인
5. [ ] 리바이 요청 3건 동시 대기 → 방장 화면에서 순서대로 처리, 중복 지급 없음(같은 버튼 연타 포함)
6. [ ] 모바일 소형 화면(세로)에서 좌석 패널·칩 추가 입력창·방 설정 입력창이 버튼과 겹치지 않는지, 키보드가 입력창을 가리지 않는지
7. [ ] 끝: 여섯 명 칩 합 = 시작 칩×6 + 승인 리바이 합. `chip_audit` 전부 `ok:true`, `seat_events_suppressed` 없음(로그 누락 없음), 서버 재시작 없음
