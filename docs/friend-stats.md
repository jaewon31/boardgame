# 친구와 함께한 홀덤 전적

> 2026-11-17 문서 정비: 현재 익명 인증은 [anonymous-auth](anonymous-auth.md)를 따른다. 아래 Google 계정 검증 설명은 도입 당시 기록이며 지금은 서로 다른 테스트 계정으로 검증한다. 최신 구현/배포 상태는 [project-status](PROJECT_STATUS.md).

친구 목록의 전적 버튼에서 함께 참여한 판 수, 각자의 팟 획득 횟수/비율과 순 칩 증감을 비교합니다. 사이드 팟 또는 나눠 가진 팟을 포함해 양수를 받은 경우 팟 획득 1회로 집계합니다. 여러 명이 참여하므로 일대일 승률이 아니며 두 사람의 획득률 합계가 100%일 필요가 없습니다. 칩 증감은 함께한 판에서 각자의 전체 순 칩 증감이며 두 사람 사이의 칩 이동만 의미하지 않습니다.

결과는 서버가 판을 완전히 끝낸 후 SQLite에 원자적으로 기록합니다. 동일 핸드 ID는 한 번만 기록하며 서버 재시작/리버 공개 중복으로 집계가 늘어나지 않습니다. 참가 당시 계정 ID를 보존하므로 중간에 나간 플레이어도 포함합니다. 대기실 관전자와 늦게 들어와 패를 받지 않은 플레이어는 제외합니다. 과거 익명 플레이는 계정과 연결할 근거가 없어 소급 집계하지 않습니다.

게임 서버와 함께 STATS_DB_PATH 파일을 영구 볼륨에 저장하고 백업하세요. 기본은 STATE_DB_PATH와 같은 폴더의 stats.sqlite 또는 ./data/stats.sqlite입니다. 한 서버/한 볼륨으로 운영하는 현재 구조의 누적 기록입니다. 서버 이동 시 통계 파일도 이전해야 합니다. 각 기기에서 같은 게임 서버 주소를 사용해야 같은 기록을 봅니다.

GET /friends/{friend UUID}/stats는 현재 유효한 Supabase 로그인과 수락된 친구 관계를 각각 확인합니다. 본인과 지정 친구가 함께한 숫자만 반환하며 카드, 이메일, 타인 전적은 포함하지 않습니다. 친구 관계 해제 즉시 조회가 거부됩니다. 클라이언트 기록 업로드 기능은 없으며 앱에서 승률을 조작할 수 없습니다.

새 Supabase SQL이나 비밀 키는 필요하지 않습니다. 이전 단계 003_single_session.sql은 적용되어 있어야 합니다. 서버 재시작 후 서로 다른 Google 계정으로 로그인하고 친구가 되어 홀덤 한 판을 끝낸 뒤 홈 > 친구 > 전적으로 확인하세요. 아직 끝난 판이 없으면 0판, 서버 연결 오류는 오류 화면으로 구별합니다.

## P2 두 친구 비교 — 2026-11-17

로컬 구현 및 자동/Chrome fixture 검증 완료. 실기기·스테이징·운영 배포는 미완료. [P2 보고서](p2-ui-friend-comparison-report.md)에 캡처·변경 파일·권한 검증 근거를 기록했다.

친구 탭의 상대 전적 비교에서 본인 또는 수락된 친구 두 명을 UUID로 선택한다. 기존 목록의 본인-친구 전적 버튼도 유지한다. 새 GET /friends/{first UUID}/{second UUID}/stats는 현재 세션을 확인한 뒤 동일 토큰으로 can_compare_friend_stats RPC를 호출한다. 조회자-첫 친구, 조회자-둘째 친구, 두 친구 상호 관계 모두 accepted여야 한다. pending/해제/삭제 계정/동일 대상은 허용하지 않는다. 매 조회에 재검증하며 카드·개인정보 없이 숫자만 응답한다. 이미 전달된 화면을 실시간 회수하지는 않는다.

위 본문의 “새 Supabase SQL 불필요”는 기존 본인-친구 API에만 해당한다. 제3자 두 친구 관계는 기존 RLS/list_friends로 확인 불가하여 [007 RPC 초안](../supabase/drafts/007_friend_stats_permission.sql)을 추가했다. 테이블·RLS·기존 데이터 변경은 없고 함수 추가만 필요하다. 운영 DB 미적용이며 적용 승인이 필요하다. RPC 미적용/장애 시 신규 API는 503으로 차단되고 기존 조회는 유지된다.

표시 항목은 두 닉네임, 공동 참여 핸드 수, 각자의 팟 획득 횟수/획득률, 공동 참여 핸드 전체 순 칩 손익이다. 획득률 분모는 공동 참여 핸드 수이고 양수 팟 지급이 있는 핸드를 1회로 센다. 엄밀한 일대일 승률이나 상대에게 직접 획득한 칩이 아니다. 마지막 대결 일시/게임 수는 기존 DB에 계산 근거가 없어 표시하지 않는다.

## 운영 전 보안 재검증

2026-11-17: [최종 보안 보고서](p2-rpc-security-review.md). 최신 007 초안은 001~006(특히 read_account_session)이 필요하다. 위 001/002만으로 가능한 초기 초안 설명은 더 이상 최신 적용 조건이 아니다. 직접 RPC 호출에도 JWT authenticated 역할·최신 세션을 확인하며 postgres owner, PUBLIC/anon/service_role revoke, 예상 밖 ACL 검사로 강화했다. 서버도 publishable key만 허용한다.

서버 178/178, 모바일 50/50, TypeScript 통과. 운영 카탈로그/JWT gateway와 독립 사용자 차단 모델은 미확인으로 운영 적용 판정은 보류한다. 저장소에는 차단 테이블/기능이 없으며 친구 삭제/pending 검사로 사용자 차단까지 완료했다고 표시하지 않는다. [읽기 전용 점검 SQL](../supabase/drafts/007_friend_stats_preflight_readonly.sql) 제공, 운영 실행 없음.

## 2026-11-18 설치 후 재검증

운영 RPC 설치 및 anon=false/authenticated=true/service_role=false EXECUTE 권한은 사용자 확인 결과다. 이전 “운영 미적용”은 당시 이력이며 최신 설치 상태를 뜻하지 않는다. [재검증 보고서](p2-rpc-verification-2026-11-18.md): 로컬 다섯 시나리오·서버 178/178·모바일 50/50·TS·웹 빌드·P1/P2 Chrome PASS. 실제 로그인 JWT E2E는 미검증. current_account_session의 account_sessions 갱신 가능성 때문에 운영 데이터 불변 조건 아래 운영 사용자 세션으로 API를 호출하지 않았다.
