## 원인

- App.tsx는 `room.room` 유무로 홈/로비를 결정했으며, 화면 위치와 방 참여 상태를 별도로 관리하지 않았다. 로비에서 참여를 유지하고 홈으로 이동하는 명시적인 경로 및 홈 복귀 카드가 없었다.
- RoomClient.restore는 SecureStore의 코드·재접속 토큰이 있을 때만 resume을 보냈다. 저장 실패, 연결 취소/응답 유실 등으로 로컬 정보가 없더라도 서버 계정의 자리가 남을 수 있었다.
- enter는 로컬 상태만 검사했다. 서버는 계정의 중복 참여를 ALREADY_JOINED로 막지만, 클라이언트는 이 오류에 로컬 정보를 지우고 홈으로 돌아가므로 복구가 불가능했다.
- leave는 서버의 left 응답을 기다리지 않고 로컬 상태/저장 토큰을 먼저 지웠다. 오프라인이거나 요청 실패 시 서버 참여는 남을 수 있었다.
- 제시된 뒤로 가기 동작 자체가 leave를 호출했다는 증거는 없었다. Android 뒤로 가기 처리도 명시되어 있지 않았다. 위의 상태 불일치 및 복구 누락은 코드와 회귀 테스트로 확인했다.

## 기존 설정과 저장 구조

기존 RoomSettingsEditor와 updateSettings WebSocket 명령이 이미 존재했다. 편집 항목은 시작 칩, 스몰 블라인드, 빅 블라인드, 턴 제한 시간 네 가지다. 방 이름 필드는 없고 maxPlayers는 서버 상수 6이다. 따라서 신규 필드나 정원 편집을 추가하지 않았다. 게임 종류는 생성 시 홀덤만 지원한다.

방장만 로비에서 수정 가능하며, 서버가 방장·수치 범위·블라인드/시작 칩 관계를 검사한다. hand가 있는 동안 수정 금지이며 기존 새 경기 준비/칩 초기화로 로비에 돌아온 후 변경 가능하다. 일반 참여자는 동일 설정 요약을 확인한다. 고정 6명 정원은 연결이 끊긴 예약 자리도 포함하여 서버가 제한한다.

방 참여와 설정의 권위 있는 저장소는 게임 서버 메모리 및 SQLite 체크포인트다. Supabase는 인증, 최신 계정 세션, 프로필과 친구 RLS/RPC에 사용된다. 방 테이블/RLS를 새로 만들지 않았고 인증 구조도 변경하지 않았다.

## 변경

- 인증된 currentRoom 명령: 클라이언트가 보낸 사용자 ID를 신뢰하지 않고 기존 authorize가 검증한 accountId/loginId로 유효한 자리를 복원한다. 다른 계정 접근은 차단한다. 새 로그인은 이전 로그인 자리를 정리하는 기존 정책을 유지한다.
- 앱 실행 시 저장 토큰 유무와 관계없이 서버 참여 상태를 조회한다. 연결 복구와 화면 활성화 때도 재확인한다. 이미 연결된 소켓은 기존 heartbeat/실시간 room 메시지를 활용한다.
- 생성/입장 전에 동일 소켓에서 참여 조회를 먼저 수행한다. 참여 중이면 joined로 기존 방을 복원한다. 조회 이후 발생한 경쟁으로 ALREADY_JOINED가 오면 다시 조회한다. 연결 중 연타는 동기 상태 검사로 차단한다.
- App의 roomOpen으로 화면 위치를 분리했다. 로비의 ‘홈으로 · 방 참여 유지’ 및 Android 뒤로 가기는 참여를 유지한다. 홈에 게임/초대 코드, 인원, 방장 여부, 설정, 복귀/나가기 카드를 표시한다. 미참여자의 기존 생성·입장 UI는 유지한다. 이름 필드가 없으므로 게임명과 코드를 표시한다.
- 나가기는 확인 대화상자 후 서버 left 응답을 받아야 로컬 참여를 지운다. 오프라인에서 나간 것으로 처리하지 않는다. 응답 유실 시 재연결하여 서버 결과를 확인한다. 마지막 참여자가 나가면 방 종료, 방장은 접속 중인 참여자 우선으로 위임하는 기존 정책을 유지한다.
- 설정 저장은 settingsUpdated 응답 후 편집기를 닫는다. 저장 중 연타를 막으며 서버 오류 시 초안을 유지하고 편집기 안에 오류를 표시한다. 확인 전에는 로컬 방 설정을 덮어쓰지 않는다. 저장 실패 시 성공 응답을 보내지 않는다.

## 배포 및 제한

Supabase SQL Editor에서 실행할 신규 SQL은 없다. 데이터 삭제/초기화 및 원격 SQL 실행도 하지 않았다.

currentRoom을 지원하는 게임 서버를 먼저 배포/재시작하고, 이후 업데이트된 앱을 사용한다. 구 서버는 신규 조회 명령을 이해하지 못한다. 서버 재시작은 기존 SQLite 볼륨/STATE_DB 설정을 유지하여 진행한다. 이 작업에서 운영 서버 재시작 또는 앱 배포는 하지 않았다.

기본 연결 해제 후 자리 보존은 5분이며 변경하지 않았다. 설정 응답이 유실되면 저장 여부가 불명확할 수 있으므로 재연결된 서버 설정을 기준으로 확인한다. 서버 저장 장치 장애는 기존 fail-closed 정책대로 로비를 중단하며 성공 응답을 보내지 않는다.
