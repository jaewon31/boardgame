## 1. 권위 있는 상태와 화면

서버 `lobby.ts`의 rooms/member/hand가 방 참여와 게임 상태의 기준이다. 각 소켓의 요청은 인증을 포함하여 순차 처리되며, 인증 대기 이후 소켓 소유권도 재검사한다. 서버 확정 스냅샷은 joined/room 메시지로 내려온다. 클라이언트는 RoomClient 하나를 useRoom에서 유지하고 홈·로비·게임에 같은 상태를 전달한다. App의 roomOpen은 화면 위치만 나타낸다.

새 상태 라이브러리를 도입하지 않았다. roomView.roomPhase는 기존 RoomState를 아래 표시 상태로 계산하며 별도 상태를 저장하지 않는다.

| 표시 상태 | 원본 상태 | 의미 |
|---|---|---|
| NO_ROOM | idle + room 없음 | 서버 noRoom/left 확인 후 생성·입장 화면 |
| CHECKING_ROOM | connecting | 현재 참여 확인 또는 입장 진행 중 |
| IN_LOBBY | connected + room + hand 없음 | 로비 참여 |
| IN_GAME | connected + room.holdem | 게임/결과/다음 판 대기 |
| RECONNECTING | reconnecting | 마지막 스냅샷을 유지하며 재확인 |
| ERROR | error/disconnected | 조회 실패·취소·재시도 소진; 미참여로 간주하지 않음 |

로그인 가능 계정이 정해지면 currentRoom을 조회한다. 앱 실행·계정 변경·포그라운드 복귀·연결 손실에 useRoom/RoomClient가 복원을 담당한다. 연결 중 반복 refresh는 추가 소켓/조회 요청을 만들지 않는다. 이미 연결 중이면 heartbeat와 room 이벤트를 사용한다. SecureStore 토큰은 비인증 레거시 resume 복구 수단으로만 남아 있고, 앱의 인증된 복원은 검증된 계정·로그인 세션을 기준으로 한다.

서버 조회 실패는 ERROR 또는 RECONNECTING이며 기존 카드/자리 정보를 미참여로 지우지 않는다. noRoom만 부재를 확정한다. previousCode가 있는 조회에 서버는 room-closed(방 자체 없음)와 membership-ended(방은 있으나 해당 참여 없음)를 구분한다. 일반 네트워크 오류에 방 종료 문구를 표시하지 않는다. 이전 코드가 없는 새 앱 실행에서는 전체 방 종료 여부를 추정하지 않는다.

## 2. 발견한 문제와 수정

- useRoom의 boolean enabled 의존성만으로는 A→B 계정 전환을 구분할 수 없었다. 계정 ID로 연결 수명을 관리하고, 렌더 시점부터 다른 계정 스냅샷을 가린다. 토큰 제공자도 연결 소유 계정과 실제 세션 user.id를 비교한다. cleanup된 연결의 콜백/인증 응답은 폐기한다. 인증/Supabase 정책은 변경하지 않았다.
- 조회 오류·취소가 idle로 돌아가 미참여와 혼동될 수 있었다. error 상태를 추가하고 홈의 확인 중/실패/다시 시도 표시를 분리했다. 취소는 참여를 지우지 않는다.
- 오래 걸리는 이전 인증 요청이 새 연결의 전송 큐를 지연시킬 수 있었다. 연결 세대가 바뀌면 큐를 분리하며 기존 세대 응답은 무시한다. dispose 이후 저장 실패도 UI에 전달하지 않는다.
- 설정 초안에 기준 버전이 없었다. settingsRevision과 expectedRevision으로 서버에서 낙관적 동시성 검증을 하고 requestId로 저장 응답을 대응시킨다. 오래된 응답/스냅샷은 최신 설정을 되돌리지 않는다. 편집기에서 최초 편집 시점의 설정·버전을 함께 보존한다.
- 설정 응답 timeout 뒤 곧바로 다른 저장을 보내면 늦은 이전 응답을 새 저장 성공으로 오인할 수 있었다. timeout은 연결을 재검증하며 서버 최신 설정을 다시 받는다.
- 체크포인트에 연결 중이던 자리의 expiresAt이 없으면 재시작 시점부터 새 5분을 주던 경로가 있었다. 마지막 저장 시각 + 자리 유예시간으로 계산하여 서버 중단/반복 재시작이 만료된 자리를 되살리지 않도록 했다.
- 만료 타이머는 현재 소켓/멤버 소유권을 재확인한다. 너무 일찍 깨어난 타이머는 남은 시간만큼 다시 예약하고, 중복 remove는 무시한다.

## 3. 방장과 일반 참여자의 동작

| 행동 | 일반 참여자 | 방장 |
|---|---|---|
| 홈 이동/뒤로 가기 | 참여·소켓 유지 | 참여·방장 유지 |
| 앱 종료/소켓 단절 | disconnected 표시, 유예시간 동안 자리 유지 | 즉시 위임/방 삭제 없이 방장 유지 |
| 유예시간 내 복귀 | 동일 계정/좌석/최신 서버 상태 복구 | 동일 자리·방장 권한 복구 |
| 명시적 방 나가기 | 서버 remove 및 left 확인 후 로컬 상태 제거 | 접속 중인 남은 참여자 우선, 없으면 첫 남은 참여자에게 위임 |
| 유예시간 만료 | 기존 depart 규칙으로 제거 | 동일 제거 후 위임 |
| 마지막 실제 참여자 제거 | 방·타이머 정리 | 동일 |

접속자 0명과 참여자 0명은 다르다. 모든 소켓이 끊겨도 유예시간 동안 예약 참여자가 있으면 방은 남는다. 최종 예약 참여자가 만료되면 방을 정리한다. 빈 방을 추가로 유지하는 별도 TTL은 없다. 기존 위임 결과는 room.hostId를 통해 모두에게 방송된다.

로그아웃/계정 변경 시 클라이언트는 이전 소켓을 폐기하고 화면에서 정보를 숨긴다. 이것을 새 계정 토큰으로 이전 방 leave를 보내는 동작과 섞지 않는다. 기존 서버의 세션 검증 실패/새 로그인 교체 정책 또는 자리 만료가 이전 참여를 정리한다.

## 4. 5분의 정확한 의미

- 서버: `RECONNECT_MS` 기본 300000ms. 기존 환경 변수 이름을 유지한다. 내부에서 seatRetentionMs로 명명하며 reconnectMs 옵션도 호환한다. 서버가 소켓 종료를 감지한 때부터 해당 플레이어의 자리와 계정 참여를 보존하는 시간이다.
- 클라이언트: retryWindowMs 기본 300000ms. 연결 손실 이후 자동 재시도 예산이다. 서버 자리 만료와 독립적이다. 수동 재시도는 새 예산으로 서버에 재확인한다.
- 소켓 응답: 연결 timeout 8초, 클라이언트 heartbeat 주기 5초/응답 유효 15초, 서버 ping 주기 15초. 이 값들은 5분 자리 유예시간과 다르다.
- 게임 턴: 기존 설정 turnSeconds와 게임 엔진 타이머가 계속 진행한다. 단절은 턴을 멈추거나 5분으로 늘리지 않는다. 만료 후 depart(폴드/퇴장 등 기존 규칙)를 실행한다. 리버 공개 및 자동 다음 판 규칙도 변경하지 않았다.

로비와 게임에 서로 다른 유예시간을 새로 도입하지 않았다. 현재 정책은 둘 다 즉시 퇴장이 아니며 무제한 보존도 아니므로, 확인된 문제 없이 시간을 바꾸지 않았다. 방 자체의 5분 TTL은 없다. 연결된 참여자가 있으면 5분이 지나도 방이 유지된다.

## 5. 앱 종료와 서버 재시작

앱 종료는 명시적 leave가 아니다. 서버가 연결 단절을 감지한 후 유예시간 안에 동일 유효 로그인으로 돌아오면 같은 자리를 받는다. 새 로그인 세션은 기존 단일 세션 정책에 따라 이전 로그인 자리를 종료할 수 있다.

STATE_DB_PATH가 설정되면 SQLite 체크포인트가 방, 계정/자리, 설정 버전, 칩, 패/덱/게임, 기록을 저장한다. production 설정은 이 경로를 요구한다. 개발 환경에서 경로가 없으면 메모리 전용이므로 서버 재시작 후 방 복구가 불가능하다.

재시작은 저장된 expiresAt을 유지한다. 마지막 체크포인트에 연결 중이던 자리는 savedAt + 유예시간까지 복구 가능하다. 만료된 자리는 새 시간으로 갱신하지 않는다. 기존 24시간 이상 오래된 체크포인트 무시 및 게임 복원 시 recoverClock/리버 복원 보호 정책은 유지한다.

단일 프로세스 + 기존 영속 SQLite 볼륨이 요구된다. 볼륨을 버리거나 서버를 여러 인스턴스로 늘리면 현재 구조의 상태 공유가 보장되지 않는다. 다중 인스턴스가 필요할 때 별도 공유 저장소·소유권/라우팅 설계를 검토해야 하며 이번 작업에서 도입하지 않았다.

## 6. 설정 동시성과 호환성

서버는 방장, hand 없음, 설정값 유효성, expectedRevision 일치를 확인한 다음 버전을 올려 영속화하고 settingsUpdated(requestId, revision)를 응답한다. 모든 참여자는 room 이벤트를 받으며 재접속도 최신 스냅샷을 받는다. 저장 실패 시 성공 응답을 보내지 않고 기존 fail-closed 정책을 따른다. 편집 초안은 서버 확정값과 분리되어 실패 시 유지된다.

설정 저장과 게임 시작이 같은 기준 버전으로 경쟁하면 먼저 처리된 요청만 기준 상태를 확정한다. 설정이 먼저 저장되면 시작 요청은 최신 설정 재확인을 요구한다. 게임이 먼저 시작되면 설정 변경이 거절된다. 게임 종료 후 새 경기 준비로 로비를 다시 열 때도 버전을 올려 이전 로비 초안을 막는다.

공유 필드는 호환 가능한 선택 필드로 추가했다. 다만 안전한 쓰기 검증을 위해 새 서버는 버전 없는 구 앱 설정 변경을 recoverable 오류로 거절한다. 새 앱도 버전 없는 구 서버에는 설정 저장을 보내지 않는다. 방 조회/입장/게임 등 기존 메시지는 유지한다. 서버를 먼저 배포한 후 앱을 업데이트해야 한다. 레거시 체크포인트에 버전이 없으면 0으로 읽으므로 SQL 마이그레이션은 없다.

## 8. 테스트 범위

기존 107개 테스트의 시나리오를 유지했다. 변경된 명령에는 expectedRevision을 넣고, 오류 상태 기대값은 idle에서 error로 조정했다. 테스트를 삭제하거나 skip하지 않았다.

| 요청 시나리오 | 자동 검증 범위 / 남은 수동 확인 |
|---|---|
| 1. 홈 이동·복귀 | 상태 공유/참여 유지 경로 유지. 실제 홈 버튼/Android 뒤로 가기는 기기 확인 필요 |
| 2. 앱 재실행 | 저장 세션 복원 및 토큰 없는 계정 조회 테스트. OS 강제 종료 후 재실행은 수동 |
| 3. 로비 네트워크 단절 | 실제 WebSocket 단절·재조회·동일 자리 복구 |
| 4–5. 방장/참여자 재접속 | 권한·좌석·인원·최신 설정 유지 |
| 6–7. 명시적 퇴장/위임 | left 확인, 새 방 생성, hostId 위임, 마지막 퇴장 |
| 8. 모든 연결 종료 | checkpoint에 예약 참여 유지 → 유예 만료 후 빈 방 정리 |
| 9. 설정 직후 재접속 | 최신 settingsRevision과 설정 확인 |
| 10. 설정/게임 시작 경쟁 | 두 처리 순서 모두 검증 |
| 11. 늦은 응답 | 이전 소켓 콜백·인증 결과·잘못된 requestId·낮은 버전 무시 |
| 12. 조회 실패 vs 미참여 | 재시도 실패는 ERROR, noRoom은 NO_ROOM, 실제 종료 사유 구분 |
| 13. 계정 격리 | 실제 표시 함수에 A→B/로그아웃 입력 및 이전 연결 인증 폐기. 실제 로그인 화면 전환은 수동 |
| 14. 유예 만료 | 로비 위임/종료와 게임 중 depart 처리 |
| 15. 서버 재시작 | 임시 SQLite의 설정/버전/좌석/패/기록 복구 및 오래된 자리 부활 방지 |

React Native 렌더/기기 터치 E2E 테스트를 실행한 것으로 간주하지 않는다. 새 라이브러리·인증 정책·게임 엔진 변경은 없다.

## 9. 수동 점검과 배포

1. 업데이트된 서버와 앱에서 방 생성 → 홈 → 복귀, Android 뒤로 가기를 반복한다. 같은 코드/좌석이어야 한다.
2. 두 계정으로 입장 후 각각 앱 종료/재실행, Wi-Fi 차단/복구, 포그라운드 복귀를 확인한다. 네트워크 오류가 방 종료 문구로 바뀌면 안 된다.
3. 방장 설정 변경 → 참여자 반영 → 참여자 앱 재실행을 확인한다. 설정 초안 저장 실패 시 초안과 서버 요약이 구분되어야 한다.
4. 로그아웃 후 다른 계정 로그인 시 이전 방 카드/패가 한 프레임도 표시되지 않는지 기기에서 확인한다.
5. 기본 유예시간을 넘긴 뒤 다시 연결한다. 방이 남아 있으면 참여 종료, 모든 참여가 끝났으면 방 종료 안내가 나와야 한다.
6. 운영과 같은 영속 볼륨을 유지한 스테이징 서버 재시작 후 복구를 확인한다. 실제 운영 재배포/재시작은 이번 작업에서 하지 않았다.

서버 재배포와 앱 업데이트가 필요하다. Supabase SQL Editor에서 실행할 신규 SQL은 없으며 DB 삭제/초기화도 수행하지 않았다.
