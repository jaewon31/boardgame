# 개발 및 작업 인수인계

1. Codex 또는 Claude Code에서 공식 저장소 루트를 연다. [AI 인계](ai/HANDOFF.md)를 먼저 읽는다. 시작 전에 `git rev-parse --show-toplevel`, `git branch --show-current`, `git status --short --branch`, `git log -5 --oneline`을 확인한다. 이미 진행 중인 파일 변경과 작업 범위를 대조한다.
2. 이어서 작업할 때는 합의된 브랜치를 사용한다. 기능 개발, 버그 수정, npm 보안 패치, 스테이징 환경 구축은 가능한 한 별도 브랜치와 커밋으로 관리한다. 기존 미커밋 작업과 분리할 때는 확인된 기준 SHA에서 목적 기준 이름(예: `fix/<작업명>`, `feat/<작업명>`; 기존 `codex/`·`claude/` 접두사도 허용)을 사용한다. 브랜치 규칙은 [공통 지침](../AGENTS.md)을 따른다. 다른 작업의 미커밋 변경을 보존하고 해당 작업의 변경만 선택한다. 겹치는 변경을 발견하면 관련 편집을 멈추고 사용자에게 알린다.
3. 변경 후 [검증 절차](testing.md)에 따라 관련 검사를 실행한다. 검증 방법과 기록 양식은 그 문서를 재사용한다. 결과에는 날짜, 브랜치·SHA·dirty 여부, 명령, 실행 환경, 결과·개수, 미실행 또는 실패 사유, 근거 경로를 남긴다.
4. 기능 상태나 우선순위가 달라졌으면 [현재 상태](PROJECT_STATUS.md)를 갱신한다. 상세 테스트 결과는 기존 기능 보고서나 해당 작업 기록에 두고 현황에서 링크한다. 다음 에이전트(Codex 또는 Claude Code)에게는 완료 범위, 남은 작업, 변경 파일, 이어서 실행할 검사와 승인 대기 항목을 [AI 인계](ai/HANDOFF.md)에 기록해 전달한다. 운영 정보는 확인 출처와 시점을 표시한다.
5. `git diff --check`, `git diff --stat`, `git status --short`로 변경을 검토한다. 사용자 승인 후 해당 작업 파일만 선택해 의도별로 커밋한다. 기존 커밋을 재작성하지 않는다. 관련 문서 변경은 해당 작업의 커밋에 포함하고 기존 상태 문서와 작업 기록을 재사용한다. 환경파일, 키, SQLite, 로그, 생성물, Supabase 연결 캐시는 제외한다. 원격 작업의 승인 경계는 [공통 지침](../AGENTS.md)을 따른다.

GitHub 브랜치와 PR의 용어는 [GitHub 안내](../GITHUB_WORKFLOW.md)에 있다. 작업 재개 시 [문서 색인](README.md)에서 관련 문서만 추가로 읽는다.
